# 手机 GUI Agent 优化方向与协作路线

> 整理日期：2026-10-17  
> 项目基础：opencyvis-phone-main  
> 当前阶段：优化方向已初步划分，具体方法待逐模块调研。  
> 文档用途：作为与其他 Agent 多轮讨论、调研、设计和后续实施的共同上下文。

## 1. 项目目标与当前约定

本项目基于 opencyvis 开发手机 GUI Agent。现有工程已提供后台执行、悬浮窗口、用户接管、虚拟显示和手机操作等基础能力，后续重点是提升 Agent 在算法、架构、交互和学习范式上的能力。

目标不仅是完成一次任务，还包括：

- 更准确地理解当前界面并定位操作目标。
- 更可靠地完成长任务，处理计划变化与中途纠正。
- 从自身执行经验中形成可复用技能。
- 从用户日常操作和接管纠正中学会原本不会的任务。
- 随使用次数增加，降低执行时间、模型调用和用户介入。
- 识别反复出现的执行瓶颈，逐步改善工具和 Harness。

当前约定：

1. 本文确定研究问题和模块边界，不代表已经选定方法。
2. 后续按模块调研、比较候选方案、实施和评估，不一次性重写整个 Agent。
3. 每次选型都应说清楚：为什么选择这个方法，替代方案是什么，增加了哪些成本，收益适用于什么场景。
4. 保持开放思维，可以引入前沿思想及其他领域的方法，但必须与具体问题建立联系。
5. 优先利用现有工程能力；是否需要多模型、多 Agent、模型训练等，通过实际需求和实验判断。
6. 项目目标是构建有能力、有特色的手机助手，避免把工作重心转移到与目标无关的过度防御。

### 2.1 模型上下文的实际组织

当前请求的整体顺序是：

```text
system prompt
历史 user 消息与 assistant 输出
当前 user 消息：当前截图 + 当前文字信息
```

- 当前任务有 `recent messages`，位于当前观察消息之前。
- 历史 assistant 输出以 JSON 文本保存，包含 thought、动作类型与参数等。
- 当前文字信息包含任务指令，以及可选界面树、执行反馈、用户回答、用户补充、全局记忆和任务笔记。
- 旧消息的截图会被移除，保留文字；历史采用 100 条消息的裁剪上限并保留系统提示。
- 新任务重新建立消息列表，不自动加载以前任务的完整聊天历史；跨任务信息主要通过长期记忆传递。
- 系统提示词包含动作说明，但正式工具 schema 通过 API 请求的 `tools` 字段传递。

旧截图移除会修改上一轮消息内容，从而缩短相邻请求的共同前缀。上下文优化需要综合比较图片开销、上下文质量、缓存复用和延迟，不能仅凭消息排序判断。

## 3. 八个优化模块

### 总体上的

上下文优化：Plan，state，感知与定位，grounding

Skill沉淀：从成功经验中提炼可迁移的技能，让同类任务越做越熟练

Memory：记忆系统的设计

学习模块：从用户日常操作学习

自进化：Harness进化与Skill进化

### 模块 1：轨迹记录与观测

**目标：** 看清 Agent 完成任务时每一步发生了什么，并为后续学习提供可靠数据。

需要观测截图、模型输出、工具调用、实际动作、执行结果、耗时、重试及用户接管。记录应尽量关联：

```text
任务与子目标
→ 动作前观察
→ 决策与动作参数
→ 实际执行
→ 动作后观察
→ 结果与用户纠正
```

重点待讨论：

- 一次任务、一个步骤和一次状态变化如何关联？
- 如何区分模型计划执行的动作与实际执行的动作？
- 如何展示截图、界面树、thought、工具参数和反馈，方便定位失败原因？
- 如何记录 Agent 与用户之间的控制权切换？
- 调试展示、长期存储和学习数据怎样共用同一套基础记录？

注意：thought 是模型对自身决策的描述，不能单独证明动作生效或任务成功。

**建议产出：** 轨迹数据格式、任务回放或检查界面、导出方式、基础任务结果标注。

### 模块 2：感知与定位

**目标：** 让 Agent 更准确地理解页面、找到目标并执行操作。

重点待讨论：

- 截图和界面树如何融合，各自在什么情况下可靠？
- 是否需要显式的页面、元素、输入状态等结构化表示？
- 目标如何从用户意图映射到具体界面元素？
- 如何应对滚动、重复文本、遮挡和布局变化？
- 是否需要按任务选择局部截图、分辨率或观察粒度？

**候选比较维度：** 纯截图、纯界面树、融合观察；坐标定位与语义元素定位；全屏观察与局部观察。这里只列比较方向，不预设方案。

**主要指标：** 定位准确率、误点率、页面变化后的成功率、观察与推理开销。

### 模块 3：任务规划与进度管理

**目标：** 支持子任务、长程任务、计划切换与中途指令调整。

重点待讨论：

- 什么时候需要显式计划，什么时候直接单步决策更合适？
- 如何表示已完成、进行中、未完成和暂时受阻的子目标？
- 什么时候继续执行原计划，什么时候局部调整或整体重规划？
- 用户中途改变目标后，哪些进度可以保留，哪些必须重新处理？
- 跨应用信息和中间成果如何传递，避免遗漏和重复劳动？

**候选比较维度：** 单步决策、显式子目标、层次化规划；固定计划与动态重规划。规划职责可以先在同一 Agent 内实现，不自动等同于引入多 Agent。

**主要指标：** 长任务成功率、子目标遗漏、无效步骤、重规划成本、中途变更后的完成率。

### 模块 4：结果验证与恢复

**目标：** 区分输入成功注入、动作达到预期效果和任务真正完成。

**当前优先级：** 可以暂时低于其他核心模块，但保留基本结果标注，为技能学习提供可信样本。

重点待讨论：

- 动作完成和任务完成分别应由什么证据判断？
- 如何区分需要等待、操作无效、定位错误与计划错误？
- 如何选择等待、换定位方式、返回、重规划或询问用户？
- 是否只有在不确定或高失败率步骤才需要额外验证？

初期可以利用用户确认、纠正记录，以及常用任务的明确结果条件。复杂验证器是否必要，依据失败分析决定。

**主要指标：** 错误宣告成功的比例、恢复成功率、额外延迟与模型调用。

### 模块 5：上下文与记忆框架

**目标：** 确定保存什么、如何管理、何时检索，以及如何让 Agent 使用记忆。

需要区分但允许相互关联的对象包括：近期消息、具体经历、当前任务状态、临时笔记、长期事实与偏好、程序性技能。

重点待讨论：

- 哪些信息进入短期上下文，哪些需要长期保存？
- 如何根据任务、应用、页面和子目标检索相关经验？
- 记忆如何去重、更新、纠正、遗忘和处理冲突？
- 记忆应在任务开始、子目标切换还是逐步决策时读取？
- 检索结果进入上下文的哪个位置，采用什么表示和预算？
- 如何兼顾上下文质量、稳定前缀、缓存复用与成本？

**候选比较维度：** 全量注入、规则筛选、相关性检索；原始历史、摘要和结构化状态。是否需要向量检索及复杂记忆架构，后续比较后决定。

**主要指标：** 相同预算下的任务成功率、无关记忆干扰、记忆准确性、上下文长度与延迟。

### 模块 6：从成功轨迹沉淀 Skill

**目标：** 从 Agent 自己的经验中提炼可迁移的技能，让同类任务越做越熟练。

重点待讨论：

- 如何从完整任务中发现可复用子流程？
- 如何确定技能的参数、适用条件、操作步骤和完成条件？
- 如何区分必要步骤、偶然步骤和绕路操作？
- 如何检索、选择、组合技能，以及处理技能失效？
- 新轨迹如何更新已有技能，避免不断重复新增？

技能可考虑表达以下内容，最终格式待调研：

```text
目标与适用条件
可变化的参数
语义步骤
关键中间状态与完成条件
偏离时的处理方式
来源经历与使用效果
```

**候选比较维度：** 原始逐步决策、检索历史示例、抽象流程指导、可执行技能。

**主要指标：** 同类任务成功率、模型调用与耗时，以及新参数、新入口、页面变化下的迁移表现。

### 模块 7：从用户日常操作学习

**目标：** 通过用户多次使用手机的经历，学到 Agent 原本缺失的知识、流程、技能与偏好。

代表性问题：某个特殊任务 Agent 暂时无法完成，但用户每天都会完成。如何利用用户几次自然操作，学会目标与流程，并在下一次独立完成？

可学习的内容：

- 操作知识：功能入口、页面关系和具体操作方法。
- 程序性技能：实现一个目标所需的步骤、分支和参数。
- 用户偏好：常用对象、默认选择与稳定需求。
- 情境习惯：某个时间、地点或任务条件下的常见行为。
- 纠正经验：用户如何修复 Agent 的错误并完成任务。

重点待讨论：

- 日常连续操作如何切分成任务，如何识别起点、终点和目标？
- 没有自然语言指令时，怎样推断用户意图？
- 多次轨迹不一致时，如何找出共同流程和合理分支？
- 如何识别试探、取消、误操作与偶然选择？
- 需要哪些证据，才能把一次行为概括为稳定偏好或技能？
- 用户改变习惯后，知识如何更新？
- 学到的内容用于推荐、补全参数还是直接执行，如何决定？

**建议起点：** 先利用有明确目标的用户示范和接管纠正，再逐步扩展到日常连续轨迹。后者需要额外解决任务切分与意图推断。

**与模块 6 的关系：** 可以共用技能表示、技能库和执行机制，但不能假设每一条用户操作都是最优动作标签。

**主要指标：** 示范次数与学习效果、未见参数下的完成率、偏好准确率、错误记忆率、后续用户纠正次数。

### 模块 8：动作组合、工具扩展与 Harness 改进

**目标：** 从使用经验中发现能力与效率瓶颈，优化高频操作的执行方式，必要时改进 Agent 的运行机制。

分成两个层次研究：

1. **技能与工具执行优化。** 将反复成功的操作组合为参数化能力，减少模型调用；明确哪些位置需要重新观察和检查，发生偏离时如何返回决策循环。
2. **Harness 改进。** 从反复失败或低效的轨迹中发现问题，提出对观察、工具接口、上下文、等待机制或执行循环的具体修改，并比较改进前后的效果。

这里的 Harness 指模型周围负责组织观察、上下文、工具、执行和反馈的运行机制。

重点待讨论：

- 哪些高频动作适合组合，组合后减少了什么开销？
- 哪些中间状态可以跳过观察，哪些必须检查？
- 如何区分缺少技能、模型决策错误与 Harness 能力不足？
- Agent 怎样提出带具体证据的改进建议？
- 如何评估一个改进在一批任务上的收益和回归？
- 哪些改进由人实施，哪些适合逐渐自动化？

期望形成的改进链路：

```text
积累执行证据
→ 发现反复出现的瓶颈
→ 提出具体候选改进
→ 比较改进前后表现
→ 将有效改进纳入系统
```

**主要指标：** 高频任务效率、能力覆盖、整体任务成功率、回归情况和维护成本。不能将更快宣告完成当作任务能力提升。

## 4. 模块关系与建议推进顺序

八个模块并非严格串行，但存在依赖：

```text
轨迹记录与评测基础（1）
├─ 支持定位、规划、验证的失败分析（2、3、4）
├─ 支持记忆与技能学习（5、6）
├─ 与用户操作观测一起支持示范学习（7）
└─ 为工具和 Harness 改进提供证据（8）

记忆管理（5）负责经验的保存与使用
技能沉淀（6）和用户学习（7）负责产生可复用知识
规划（3）负责在任务中选择与组织技能
工具与 Harness（8）负责改善能力的执行方式
```

建议阶段如下，可依据真实失败分布调整：

| 阶段 | 工作重点 | 阶段性证据 |
|---|---|---|
| A | 轨迹记录、可观测性与基础结果标注 | 能解释一次任务每一步发生了什么，并归类主要失败原因 |
| B | 感知定位、规划进度、必要的上下文管理 | 在固定任务集上展示可靠性或长任务能力提升 |
| C | 成功轨迹沉淀技能、相关经验检索 | 同类任务在新参数或新入口下更快、更稳 |
| D | 用户示范与接管纠正学习 | 原本不会的任务，在少量示范后能够复用所学技能 |
| E | 日常任务发现、习惯学习、组合工具与 Harness 改进 | 学习和优化带来持续收益，并能解释适用范围 |

模块 4 的复杂方案暂缓，但基础结果标注贯穿全程。模型微调或其他参数训练也是可选方向，是否开展取决于数据、评测和实际瓶颈。

## 6. 方法选型与评估要求

每个模块的方案都应回答：

1. **问题证据：** 当前方法在什么具体场景失败或低效？
2. **目标：** 本次要改善哪个指标，有哪些指标不能明显退化？
3. **替代方案：** 现有方法、最简单改进和其他候选方法分别是什么？
4. **选择理由：** 方法解决了哪个机制上的问题，依赖哪些假设？
5. **成本：** 增加多少推理调用、延迟、上下文、数据或维护工作？
6. **验证方式：** 如何证明提升来自本次改动，而非换模型或任务变简单？
7. **适用边界：** 哪些情况有效，哪些情况仍然失败？

比较时尽量固定模型、任务条件和可用预算，并同时报告成功率与成本。对技能和用户学习，区分用于学习的轨迹与用于检验迁移的任务；至少考察新参数、新起始状态或不同时间的执行，避免只证明记住了原样任务。

可按模块选用的公共指标：任务成功率、定位错误、无效操作、错误完成判断、执行时间、模型调用、上下文开销、用户介入、示范次数及迁移效果。不要求每次实验测量全部指标。

## 8. 期望最终展示的能力

一个具有代表性的完整演示可以是：

1. Agent 首次遇到某个任务，暴露具体能力缺口。
2. 用户通过正常操作或接管完成任务，系统记录相关经历。
3. 系统从多次经历中提炼可复用知识与技能。
4. Agent 面对新参数或新入口时，利用技能独立完成任务。
5. 随着执行次数增加，任务保持正确，模型调用、执行时间或用户介入逐渐减少。
6. 系统识别反复出现的效率瓶颈，提出并验证工具或 Harness 改进。

以上是项目目标，不是当前已实现能力。后续应逐项用记录和实验建立证据。
